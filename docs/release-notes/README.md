# release-notes/

放**面向使用者**的 Release 说明，文件名 = 版本号：

```
docs/release-notes/v0.1.0.md
```

版本号与 [CHANGELOG.md](../../CHANGELOG.md) 头部一致；打 tag 时把 CHANGELOG 的
`## [未发布]` 段改成 `## [版本号] — <日期>`，并把本目录下的同名文件作为 Release 说明。

## 为什么要单独放一份

`CHANGELOG.md` 是**开发者记录**：症状 / 根因 / 改法 / 验证结果 / 踩坑。
Release 说明是**给使用者看的**，要短、写成清单、只讲「我现在能拿到什么」。
两者受众不同，不能一份两用（见 [DOC-RULES.md](../DOC-RULES.md) §2 的禁止重复清单）。

本仓的「使用者」是**这台设备的主人** —— 他关心的是：
「现在有哪些脚本、出事了怎么一条命令恢复、哪些坑别再踩」。

## 形状

**清单，不是文章。** 开头一句加粗概述，`## 本版内容` 下按分区一行一条，
最后是固定尾巴。

```markdown
**首版：把设备侧运维脚本与 mihomo 诊断工具整理成能独立看懂、能独立演进的仓库。**

## 本版内容

**文档**

- 新增 架构说明 —— 三个域各解决什么问题、脚本会改设备哪些状态、配置怎么读。
- 新增 排障手册 —— 八个高频现象，各配可直接粘贴的排查命令。

**脚本**

- 调整 guardian.sh —— 守护 v3 移入 `guardian/`；只做「检测 + 最小化修复」，行为零变更。

---

需要 OpenWrt + ShellCrash（或任何 mihomo 内核的部署）。
`openwrt/` 的脚本会直接改路由器状态，执行前请先看 [架构说明](../ARCHITECTURE.md) 的「会改什么」。

---

> 风险提示：本仓库的脚本会直接修改路由器的系统状态（重启服务、重载防火墙、改 crontab、
> 切换代理策略组）；仓库中记录的部分凭据为明文。执行前请确认已备份，
> 详见 [凭据与安全须知](../SECRETS.md)。
```

结尾那两行是**固定尾巴**，每版照抄不动（法律留痕：持续提示、提示在先），
**不算重复内容**。

### 一条怎么写

```
新增 / 调整 / 修复 / 优化 + 对象名 —— 入口或位置；一句话你拿到什么
```

- **动词只有四个**：新增（以前没有）、调整（行为、默认值、位置变了）、
  修复（以前不对，**含底层与实现层**）、优化（你更能感知的更快 / 更小 / 更顺）；
  另有「移除」用于删功能。都写全称 —— 单字「修」读着不像词。
- **对象名照抄仓库里的实物**（文件名 / 文档名 / 脚本名），不加引号书名号，
  也不另起一个说法。
- **入口**写你找得到的位置：「仓库根 README」「docs/ 索引」；
  不需要找入口的（脚本、命令），改写场景（「路由器上」）。
- **一句话说完你拿到什么**。不写怎么用、不写为什么。
- 说人话。「`coredump`」「`SIGKILL`」这类只对开发者有意义的词别写；
  真要交代限制，写你看得见的后果（「重启后自动恢复」）。
- 一行一条。两句才说得清 → 拆成两条，或者这条本来就该留在 CHANGELOG。

## 底层与内部改动：算「修复」，而且要拆开写

这条是给「你看不出区别、但仓库确实改了」的改动定的。**它们也算本版内容，
必须写；而且要一条一条拆开，不许打包成一句。**

| 改了什么 | 动词 | 一行怎么写 |
|---|---|---|
| 底层缺陷（竞态、路径写错、时序、量纲） | 修复 | 写「以前会怎样」的后果，不写根因 |
| 重构 / 移动目录 / 改路径（行为零变更） | 修复 | `修复 仓库结构 —— 哪几处搬到哪，行为零变更` |
| 删死代码、删一次性残留 | 修复 | `修复 死代码 —— 删了哪几处，行为零变更` |
| 文档口径纠错 | 修复 | 写纠了什么口径，不写讨论过程 |
| 文档 / 规范类（规则正本、索引、声明） | 调整 | `调整 文档 —— …`；你看不到的也照写 |
| 你能感知的更快 / 更小 / 更顺 | 优化 | 写「快在哪」，并给数字 |

**禁止写法**：

- ❌ `优化 代码整理 —— 目录按职责拆分，行为零变更`
  —— 三个改动压成一句，对不上 CHANGELOG，下个版本没人知道搬了哪些文件；
- ❌ `优化 稳定性 —— 已知问题全部清零，细目见 CHANGELOG`
  —— 「细目见 CHANGELOG」等于没写；
- ✅ 拆成 4~6 行，每行一个对象，行尾该标「行为零变更」的就标。

一句话记法：**凡是在 `git diff` 里出现过的东西，说明里都要有一行**。
写不长不是本事，漏了才是问题 —— 篇幅红线排在覆盖率之后。

## 覆盖率红线

**凡本版改过的东西，必须全部出现在 Release 说明里**，动词四选一（新增 / 调整 /
修复 / 优化），一行一条。没有例外：

- 脚本行为变化 → 并进「脚本」分组，一行写「改了哪 + 你能感知的后果」
- 文档新增 / 改名 / 删改 → 并进「文档」分组，照写
- 纯搬迁 / 纯重构（行为零变更）→ 并进「修复」分组，**按对象拆成多行**
- 保留策略、备份区的处置 → 并进「运维」分组，照写

写完拿 CHANGELOG 对应段落逐条对：**CHANGELOG 里的每一处用户可感知改动，
Release 说明里都得能找到对应行**。

### 篇幅

- 覆盖率红线优先于篇幅：先保证**一条不漏**，再谈合并。
- 分组按**本仓的目录/对象**走（文档 / 脚本 / 运维 / 规则），不按轻重排。
- 合并手法：同一对象的多个小改动并成一行，但要把对象都列出来。

## 别写这些

| 别写 | 为什么 |
|---|---|
| 第二人称叙述（「点一下就…」「你可以在…里改」） | 用户要的是有什么，不是操作步骤；步骤归 README 与排障手册 |
| 「原来是这样，所以现在…」的原因与取舍 | 解释属于 CHANGELOG |
| 实现原理、脚本内部机制 | 同上 |
| 「改完要不要重启」 | 通用信息，不随版本变 |
| 「之前是什么样」的对比 | 只有修复条目允许一句症状（「连上了没网」），其余不写 |
| 「本版没有破坏性变更，直接覆盖安装」 | 没变更就不用声明；**有**的时候才必须写 |
| 凑数的「注意」区块 | 见下 |

## 「注意」区块：能不写就不写

只在**你不知道就会出问题**时才写，最多一两条：

- ✅ **有破坏性变更** —— 脚本换了调用方式、目标路径变了、要先停守护。**必须写**。
- ✅ **已知的、会被当成新 bug 的问题** —— 如实写一条，免得被重复报。
- ❌ 每版都一样的操作提醒 —— 不写。风险提示**例外**：每版说明末尾固定附风险提示段，
  属固定尾巴，不算重复内容。

## 改已经发出去的说明

已发布的说明可以重写后覆盖（说明文件与 tag 一起改）。
改完记得同步 CHANGELOG —— **说明与 CHANGELOG 不一致时，以 CHANGELOG 为准**，
并把说明补齐。

> 本仓当前**未接入自动发布流水线**（尚未上传远端，也未 `git init`）。
> 发版 = 打 tag + 手工把 `docs/release-notes/<版本>.md` 贴进 Release 页面。
> 流水线接入后，这一段需要重写。
