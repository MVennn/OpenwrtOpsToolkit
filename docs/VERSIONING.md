# 版本命名规范

> **一句话**：有没有「功能更新」决定动哪一位 —— **有功能更新进次版本（+0.1.0），
> 没有就进补丁版本（+0.0.1）**；本仓的版本号是**仓库发布号**，
> 只在 [CHANGELOG.md](../CHANGELOG.md) 的版本标题里维护。

适用范围：本仓的**仓库发布号** —— [CHANGELOG.md](../CHANGELOG.md) 的版本标题、
Release 说明文件名、发版 tag，三处**必须一致**。

本仓是脚本与配置仓库，**没有构建产物**：没有 `versionName` / `versionCode` 之类
从构建里读出来的版本号，别去任何配置文件里找它 —— 版本号是**手工维护的发布号**。

---

## 1. 三段式与进位规则

版本号是三段式：`主版本.次版本.补丁版本`（如 `0.1.0`）。

| 这次发版包含…… | 动哪位 | 写法 | 例子 |
|---|---|---|---|
| **没有功能更新** —— 只修 bug、改规则顺序、调参数、改脚本内部实现、改文档 | **补丁版本 +0.0.1** | `x.y.z` → `x.y.z+1` | `0.1.0` → `0.1.1` |
| **有功能更新** —— 新增了使用者可感知的新能力，或现有能力的行为变了 | **次版本 +0.1.0**，补丁归零 | `x.y.z` → `x.y+1.0` | `0.1.0` → `0.2.0` |
| **破坏性变更** —— 现有用法不再成立（配置格式不兼容、脚本调用方式变了、目标路径变化） | **次版本 +0.1.0**，并在 [CHANGELOG.md](../CHANGELOG.md) 的版本段落里**显式标注** | `x.y.z` → `x.y+1.0` | `0.1.0` → `0.2.0` |

进位是**连锁**的：次版本进位时补丁必然归零（`0.1.0` 的下一次功能更新是 `0.2.0`，
不是 `0.2.1` 也不是 `0.1.2`）。

## 2. 怎么判断「有没有功能更新」

判断口诀：**看这一版使用者拿到的「能做什么」有没有变 ——**

- 使用者能找到一个**以前没有的东西**（新脚本、新子命令、新配置项、新的文档正本），
  或者某个现有能力**行为 / 入口 / 调用方式不一样了** → 有功能更新 → `+0.1.0`；
- 翻遍也找不到任何新东西，改的是「做得对不对」（修复）与
  「写得清不清」（文档 / 口径 / 参数） → 没有功能更新 → `+0.0.1`。

边界情况：

| 情况 | 算不算功能更新 | 理由 |
|---|---|---|
| 修一个「本该生效却没生效」的 bug | ❌ `+0.0.1` | 行为回到了它本来该有的样子，不是新行为 |
| 删掉某项能力 / 某个脚本 / 某个入口 | ✅ `+0.1.0` | 能力清单变了，使用者可感知的减法也是更新 |
| 新增 / 删除 / 改名一个脚本，或改了调用方式 | ✅ `+0.1.0` | 使用者手上的用法要跟着改 |
| 只改文档、只改注释、只动 CI 配置（脚本一个字节没变） | ❌ 连补丁版本都不给 | 见 §5：这类改动**根本不动版本号** |
| 破坏现有用法（配置格式不兼容、目标路径变化） | ✅ `+0.1.0` + CHANGELOG 显式标注 | 见 §1 第三行 |

拿不准时问一句：**写这一版的 Release 说明时，会不会出现「新增 / 变更 / 移除了某能力」
这样的句子？** 会 → `+0.1.0`；全文只有「修复 / 调整 / 优化」→ `+0.0.1`。

## 3. 版本号在哪维护

**只有一处：[CHANGELOG.md](../CHANGELOG.md) 的版本标题**（形如 `## [0.1.0] — 2026-10-20`）。

本仓**没有构建产物版本号**，因此：

- 版本号**不从任何构建产物里读**，也没有第二个「真正的版本号」藏在别处 ——
  改版本号 = 改 [CHANGELOG.md](../CHANGELOG.md) 的段标题；
- 由它派生出两处**必须与标题一致**的引用：
  - Release 说明文件名 [docs/release-notes/0.1.0.md](release-notes/0.1.0.md)
    （**不带 `v` 前缀**，`v` 只属于 tag；格式正本见 [docs/release-notes/README.md](release-notes/README.md)）；
  - 发版 tag（`v0.1.0` 形式，tag 名 = 版本号）。

## 5. 不发版的时候：不要动版本号

**只改文档、只修拼写、只动 CI 配置 —— 脚本与配置一个字节没变 → 不动版本号。**
（本节是「什么时候不动版本号」的**正本**；其余位置只留一句话 + 链接。）

这类改动只在 [CHANGELOG.md](../CHANGELOG.md) 顶部的 `## [未发布]` 段**追加一条**，
**不新开版本段落**。理由：版本号是给使用者看的「这次拿到了什么」的标记，
文档措辞与流水线的修正不改变使用者拿到的东西。

本仓特有的原因：版本号是**手工维护**的（见开头「适用范围」—— 没有构建产物可读），
开一个版本段就等于消耗一个号。为顺手发一份纯文档改动而吃掉 `0.1.1`，
下一个真正的脚本修复就得跳到 `0.1.2`，CHANGELOG 的版本历史从此和 tag 对不上。

`[未发布]` 段攒够了再发版：把段标题改成 `## [x.y.z] — <发版日期>`，
并补一份**同名**的 Release 说明（文件名不带 `v` 前缀，
见 [release-notes/README.md](release-notes/README.md)）。

## 6. 与 CHANGELOG 的关系

| 主题 | 唯一正本 | 其余位置怎么写 |
|---|---|---|
| **版本号本身**（当前是哪个版本、历史上有哪些版本） | [CHANGELOG.md](../CHANGELOG.md) 的版本标题 | 只留一句话 + 链接，不复制版本历史 |
| **进位规则**（下一次该动哪一位） | 本篇 §1 与 §2 | 只留一句话 + 链接，不抄表格全文 |

两处都写全文，迟早各改各的 —— 单一正本原则见 [docs/DOC-RULES.md](DOC-RULES.md)。
